# Фронт сказок: миры и оформления, фронт вне ядра, какие репозитории

Ветка `think/bj-front-skins`, 2026-10-20. Рассуждение, код не трогаем.

## Вопрос

Мысль директора, 2026-10-20:
- мы делаем не просто сказки, а **сказочный мир**, а миров у сказок много;
- пользовательскому фронту нужна атмосфера — **мульти-скин**;
- пользователь выбирает оформление из списка созданных, админ тоже может выбирать;
- оформления лежат папками в репозитории, а админ добавляет в список новые репозитории;
- весь фронт, скорее всего, выносим из ядра в отдельные репозитории: web PWA, Android, Apple.

## Что есть сейчас

| Что | Где | Что важно для оформлений |
|---|---|---|
| Экран сказки: книга, кинорежим, кабинет | `orb-tale-servo/screen` | уже PWA (`manifest.webmanifest`, `sw.js`); цвета — около 30 переменных CSS (`--room-bg`, `--ink`, `--ember` …) в `tale.css`, есть светлая и тёмная тема |
| Оболочка, панель админа `/admin/`, фронт по бланкам | `bhendho/web` | общий фронт движка, выпускается вместе с ядром |
| Разметка кабинета (карточки, разделы, меню) | ядро → SDK TS `views.ts` | рисует оболочка, классы `og-*` |
| Посадочные страницы | `orb-tale-land` + `orb-tale-pages` | уже есть готовая механика «папка в git → проверка → выкладка → раздача статики» |

Получается, что начинать с нуля не придётся: цвета уже вынесены в переменные, а механика выкладки статики из git
готова у посадочных страниц.

## 1. Что такое «оформление» (скин)

Скин — **папка данных, без кода**. Раскладка — по образцу pages-v2:

```
<репозиторий оформлений>/
  forest/                 имя скина = имя папки
    skin.json             название по языкам, превью, автор, версия, светлый/тёмный
    tokens.css            только переменные: --room-bg, --ink, --ember …
    img/                  фон комнаты, рамка книги, орнаменты, обложка по умолчанию
    fonts/                свои шрифты
    sound/                по желанию: фон, звук перелистывания
  new-year/
  template/               заготовка для ИИ и человека, как template/ у посадочных
```

Уровни, от простого к сложному:
1. **Цвета и шрифты:** скину достаточно `tokens.css`.
2. **Картинки:** фон, рамка книги, орнаменты. Экран сказки показывает их через переменные
   (`--room-image: url(img/room.webp)`).
3. **Звук и анимация** — позже.

**Отговариваю от скинов со своим JavaScript и произвольным CSS.** Скин открывается в сессии пользователя, а в
ней ключ входа и кошелёк. Чужой скрипт из стороннего репозитория мог бы списать GC или увести ключ. Произвольный
CSS тоже опасен: через `url()` он умеет отправлять данные наружу и может спрятать или подменить кнопку оплаты.
Предлагаю правило: в скине **только переменные из нашего списка и файлы разрешённых типов**. Проверка — такая же,
как `land check`: одна и та же на стенде, в хуке выкладки и в службе раздачи. Список переменных — контракт:
он версионируется (`skin-v1`), как формат страниц.

## 2. Два уровня: оформление человека и мир сказки

«Миров много» можно понять двумя способами. Они не исключают друг друга:

| Уровень | Что | Кто выбирает |
|---|---|---|
| **Оформление** | как выглядит весь фронт человека: комната, шапка, кабинет | человек в кабинете; админ задаёт оформление по умолчанию |
| **Мир сказки** | у самой сказки свой мир: лес, море, космос; книга открывается в нём | выбирается при создании сказки, хранится в сказке |

Мир сказки ближе к «сказочному миру»: открыл новогоднюю сказку — снег, открыл морскую — волны. Но этот уровень
сложнее, потому что мир записывается в факт сказки, а это поле бланка подразделения.

**Предлагаю:** сначала только оформление (уровень 1). Мир сказки — следующим шагом, на том же формате скина:
сказка просто ссылается на имя скина.

Связь с посадочными страницами напрашивается сама. Посадочная `new-year` ведёт на сайт с меткой, а фронт может
сразу открыться в оформлении `new-year`. Нужен ещё один параметр в ссылке «Начать» (`&skin=new-year`), а
посадочным страницам ядро для этого по-прежнему не нужно.

## 3. Кто выбирает и где это хранится

- **Человек:** список в кабинете, превью у каждого скина. Пока человек не вошёл, выбор живёт в браузере; после
  входа хранится у него в настройках, чтобы с телефона и с компьютера было одинаково. Где именно в ядре держать
  настройки человека, проверю по коду. Кандидат — факт пользователя «настройки» у подразделения сказок, тогда
  ядро менять не придётся.
- **Админ:** в панели видит все скины из подключённых репозиториев и решает:
  - включён скин или нет;
  - какой скин по умолчанию;
  - по желанию — порядок в списке.
- **Платные скины** (за GC) — возможны позже: ядро уже умеет списывать. Сейчас не предлагаю.

## 4. Списки репозиториев оформлений

Директор предлагает, чтобы админ сам добавлял репозитории. **Здесь отговариваю от одного:** добавлять
произвольный адрес git прямо в панели. Это открывает дверь в цепочку поставки: подменили репозиторий — у всех
пользователей новое оформление. Предлагаю так:

- список репозиториев — файл `skins.yaml` в настройках сборки на сервере: адрес, ветка или тег;
- служба оформлений забирает репозитории по списку и проверяет каждый скин;
- выкладывает скины по версии: `/skins/<скин>/<версия>/…`, чтобы старая версия у людей в кэше не ломалась;
- админ в панели видит, что пришло, и включает или выключает скины;
- добавить репозиторий в список может только тот, кто правит настройки сервера, то есть продавец.

**Механику не пишем заново, а берём у посадочных страниц** (`orb-tale-land`): там уже есть проверка, выкладка
по коммиту, переключение и откат, раздача статики. Возможно, это одна служба «статика из git» с двумя видами
содержимого: страницы и скины. Это решение уровня кода, его примем на шаге.

## 5. Фронт — вон из ядра?

Сейчас в ядре `bhendho/web` лежат оболочка, панель админа и фронт по бланкам. Экран сказки уже отдельно, в
`orb-tale-servo`.

| Что | Куда | Почему |
|---|---|---|
| **Пользовательский фронт:** оболочка для человека, кабинет, экран сказки, скины | **из ядра — в свой репозиторий** | это лицо продукта сказок, оно меняется часто и живёт своими выпусками |
| **SDK фронта TS:** типы, клиент API, рисовальщик разметки | **остаётся в ядре** | это контракт ядра, выпускается вместе с ним по тегу |
| **Панель админа** | **предлагаю оставить в ядре** | она общая для любого подразделения и привязана к API ядра версия в версию; вынести можно позже, если появится второй продукт со своей панелью |

**Здесь отговариваю от выноса «всего фронта»:** панель админа без ядра бесполезна и ломается при каждой правке
API. Ядру удобно выпускать её вместе с собой. Вынос пользовательского фронта меняет то, что поставляет ядро:
`bhendho` — строгий, поэтому это отдельное решение директора и отдельный PR.

Попутно уйдёт копия общих файлов `screen/src/lib`: фронт сказок будет брать их из SDK по тегу.

## 6. Какие репозитории

| Репозиторий | Что | Когда |
|---|---|---|
| `orb-tale-web` | пользовательский фронт сказок, PWA: оболочка, кабинет, книга, поддержка скинов; сюда переезжает `orb-tale-servo/screen` | первым |
| `orb-tale-skins` | оформления папками, `template/`, `AI.md` для генерации, `make check` и предпросмотр — как `orb-tale-pages` | вместе с первым |
| `orb-tale-android` | обёртка PWA для Google Play и RuStore (Trusted Web Activity) — почти без своего кода | когда PWA устоится |
| `orb-tale-ios` | обёртка для App Store (например, Capacitor) | последним, после решения об оплате |

Имена технические, переименуем потом.

**Предлагаю PWA первым и долго единственным:**
- PWA уже ставится на телефон с Android и iPhone прямо из браузера, со значком и без сети;
- один код вместо трёх;
- обновляется без проверки в магазинах.

**Отговариваю от своих приложений Android и Apple «с нуля», то есть от трёх кодовых баз:**
- **Деньги.** В магазинах приложений покупка цифрового товара (наши GC) обычно должна идти через их оплату,
  с комиссией порядка 15–30 %. Robokassa и Stripe внутри приложения могут не пропустить. Это бьёт прямо по цене
  сказки, а значит, до решения по оплате в магазинах приложения выпускать нельзя. Правила магазинов и стран
  меняются, перед шагом проверим заново.
- **Плата за кабинеты разработчика:** Apple — ежегодная, Google — разовая. Плюс проверка каждой версии.
- **В России** App Store и оплата Apple ограничены, а для Android есть RuStore.

Если приложения понадобятся, это обёртки над тем же PWA: код один, оформления общие.

## Шаги — набросок, не в работе

| Шаг | Что | Где |
|---|---|---|
| F1 | формат `skin-v1`: `skin.json`, список переменных, разрешённые файлы, проверка `check` | `orb-tale-skins` (+ проверка в службе) |
| F2 | экран сказки берёт цвета, картинки и шрифты из скина; два скина для проверки: нынешний и `new-year` | `orb-tale-servo/screen` |
| F3 | служба оформлений по `skins.yaml`: забрать, проверить, выложить по версии | рядом с `orb-tale-land` или в нём |
| F4 | выбор скина в кабинете; хранение выбора; админ — включить, выключить, по умолчанию | фронт сказок, панель |
| F5 | вынос пользовательского фронта в `orb-tale-web`; SDK по тегу | решение директора по ядру |
| F6 | `skin=` в ссылке посадочной страницы | `orb-tale-land`, фронт |
| F7 | мир сказки: сказка ссылается на скин | бланк сказок |
| позже | `orb-tale-android` (TWA), затем `orb-tale-ios` | после решения по оплате в магазинах |

## Рекомендация

1. Скин — только данные: переменные из нашего списка и картинки. Чужого кода и произвольного CSS нет.
2. Сначала оформление человека, потом мир сказки.
3. Репозитории оформлений перечислены в настройках сервера, а не вводятся в панели. Админ включает и выключает
   то, что пришло.
4. Из ядра выносим пользовательский фронт; SDK и панель админа остаются в ядре.
5. Сначала два репозитория, `orb-tale-web` и `orb-tale-skins`. Android и iOS — обёртками PWA, после решения об
   оплате в магазинах.

## Вопросы директору

1. **Мир:** «миров много» — это оформление всего фронта человека, мир каждой сказки или оба (рекомендую оба,
   по очереди)?
2. **Кто делает скины:** мы и ИИ по заготовке, как посадочные страницы? Или со временем и сами пользователи?
   Если пользователи, нужна модерация, и это отдельная большая тема.
3. **Насколько глубоко:** только цвета, шрифты и картинки или ещё звук и анимация?
4. **Панель админа** остаётся в ядре (рекомендую) — согласны?
5. **Приложения в магазинах:** когда они нужны и готовы ли вы к оплате через магазин с его комиссией?
